# Story Capture Guidelines

This repo is a solo practitioner's story capture, not an open contribution project — but if you're sharing it with a co-author or collaborator, here's the shape stories should take.

## What makes a good story

- **Specific, not general.** "Documentation was messy" is not a story. "We assumed 40% of controls were documented; discovery showed they weren't" is.
- **Real, not composite.** Don't blend two incidents into one for effect. If it didn't happen this way, don't write it this way.
- **Honest about the mess.** The value of this playbook is that it's not the polished framework version. Include what went wrong, not just what worked.

## Format

Use `resources/story-template.md`. Seven sections: Assumption, Reality, Why It Matters, Decision, Lesson, Time Investment, Context.

## Anonymization

If a story involves identifiable people, clients, or employers who haven't agreed to be named publicly, anonymize: describe roles and organization types generically ("a regulated financial services firm," "the compliance lead") rather than using real names, unless you have explicit permission to name them.
